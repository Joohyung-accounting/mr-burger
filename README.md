# Mr. Burger

Overcooked식 주방 운영 게임. **요리사 한 명이 주방을 돌아다니며** 전광판에 뜬 주문을 쳐냅니다.
난이도는 "무엇이 들어가는지 외우기"가 아니라 **동선과 타이밍**에서 나옵니다.

의존성 0개. 순수 HTML/CSS/Canvas/JS. 빌드 단계 없이 바로 실행되고, Capacitor로 감싸면
그대로 Android AAB가 됩니다. 이미지·오디오 에셋도 0개 — 재료도 요리사도 캔버스 패스로,
효과음은 WebAudio로 런타임에 생성합니다.

---

## 바로 실행

```bash
npm run dev          # http://localhost:5173
```

`www/index.html`을 브라우저에서 그냥 열어도 동작합니다 (ES 모듈 미사용, `file://` OK).

## 테스트

```bash
npm test             # 규칙·경제 53개 + 런타임 스모크 46개
```

웹 배포는 [DEPLOY.md](DEPLOY.md) — Cloudflare Pages 설정이 저장소에 들어 있습니다.

## 화면을 파일로 찍기

```bash
node tools/serve.js 5173 --shots
```

`--shots`를 켜면 개발 서버가 문 두 개를 엽니다. **앱에는 아무것도 들어가지 않습니다.**

| | |
|---|---|
| `GET /__shot.html` | index.html 앞에 rAF 심을 하나 끼운 것. 아무도 안 보는 탭은 합성이 안 돼서 `requestAnimationFrame`이 영영 안 불립니다 — 주방 캔버스가 아무리 기다려도 빈 채로 남습니다. `setTimeout`은 숨은 탭에서 1초로 클램프돼 (루프가 `dt`를 자르니) 영업이 20배 느려지므로, **MessageChannel** 홉으로 돌립니다 |
| `POST /__shot` | data URL을 받아 `www/__shot.png`로 씁니다 (gitignore 대상) |

심이 페이지에 `__shot()`도 하나 쥐여줍니다. 껍데기는 DOM이라 SVG `<foreignObject>`를
지나가야 하는데 — 이 저장소가 주석에 쓰는 `----` 자를 걷어내고(XML은 이중 하이픈을
허용하지 않습니다), 스타일시트를 인라인하고, 애니메이션을 고정해야 합니다
(스냅샷은 모든 애니메이션을 t=0에서 뜨는데 `.sheet`와 `.ticket`은 opacity 0에서 시작).
캔버스는 그 여행에서 살아남지 못하므로 **앱의 실제 z순서대로 다시 붙입니다** —
주방은 DOM 아래, 티켓·상점 미리보기는 자기 카드 위, 열린 시트가 가린 것은 빼고.

- `test/core.test.js` — 재료 구획, 주문 생성, 채점, 그릴 곡선, 하치 매칭, 난이도 곡선,
  **20~25일치 영업 시뮬레이션**
- `test/smoke.test.js` — DOM을 스텁해 게임을 부팅하고, 캔버스를 실제로 탭해서
  요리사를 걷게 하고, 굽고, 담고, 하치까지 나르며 하루를 끝까지 돌립니다

## 주방

```
┌──────────────────────────────────────┐
│  DAY 8    $0.00 / $36.00   ❤❤❤❤❤     │
├──────────────────────────────────────┤
│            O R D E R S               │  전광판 — 버거 + 재료 이름 + 인내심 바
│    🍔       🍔       🍔                │
├──────────────────────────────────────┤
│  BUNS & PATTIES                      │
│      [빵]  [패티]                     │  ← 재료 선반 (구획별)
│  TOPPINGS                            │
│    [치즈] [양상추] [양파]              │
│  SAUCES                              │
│         [마요]                        │
│ ┌GRILL┐   ▓▓▓▓▓▓▓▓▓   ┌PLATES┐       │
│ │ 🥩  │   ▓▓ 🧑‍🍳 ▓▓    │  🍔  │       │  그릴(왼쪽) / 접시(오른쪽)
│ │ 🥩  │   ▓▓▓▓▓▓▓▓▓   │ EMPTY│       │  가운데는 걸어다니는 체크무늬 바닥
│ └─────┘               └──────┘       │
│ [🗑]        ▲  S E R V E  ▲          │  쓰레기통 / 서빙 창구
└──────────────────────────────────────┘
```

### 조작은 규칙 하나뿐

**탭한 곳으로 요리사가 걸어가서 그 스테이션을 사용합니다.**
모든 스테이션이 같은 규칙을 씁니다 — **빈손이면 받고, 손에 뭔가 있으면 준다.**

| 스테이션 | 빈손 | 뭔가 든 손 |
|---|---|---|
| 재료통 | 그 재료를 집는다 | 거절 (손이 참) |
| 그릴 | 다 구워진 패티를 집는다 | 생패티면 올린다 |
| 접시 | 접시째 든다 | 재료를 올린다 / 접시를 내려놓는다 |
| 서빙 창구 | 거절 | 접시면 내보낸다 |
| 쓰레기통 | 거절 | 버린다 |

걷는 데 걸리는 시간이 곧 게임의 부하입니다. `Running Shoes` 업그레이드가 그걸 줄여줍니다.

좌측 상단 **⏸ 버튼**으로 언제든 멈출 수 있습니다 — 손님 인내심 타이머도 그릴도 같이 멈춥니다.
일시정지 메뉴에서 **그날 다시 시작 / 사운드 토글 / 타이틀로 나가기**를 할 수 있습니다.

### 재료 — 빵 · 토핑 · 소스

선반이 세 구획으로 나뉘어 있고, 그날 쓰는 재료만 나옵니다 (최대 8통).

| 구획 | 재료 |
|---|---|
| **BUNS & PATTIES** | 빵, 패티 (항상 나옴) |
| **TOPPINGS** | 치즈, 양상추, 토마토, 양파, 피클, 베이컨, 할라피뇨, 계란후라이, 아보카도 |
| **SAUCES** | 케첩, 머스터드, 마요, BBQ |

**빵은 진짜 재료입니다.** 빠뜨리면 접시 위에 속재료만 벌거벗은 채로 쌓입니다 —
따로 경고가 뜨지 않아도 한눈에 보입니다.

### 서빙은 자동 매칭

접시를 창구에 가져가면 **대기 중인 주문 중 가장 잘 맞는 것**으로 나갑니다 (Overcooked와 동일).
"이 접시는 몇 번 손님 것"을 따로 지정할 필요가 없습니다.
엉뚱한 버거를 내면 그 자리에서 반품되고 하트가 하나 깎입니다.

### 페널티 — 무엇이 잘못됐는지 이름을 붙여줍니다

주문은 **재료의 집합**입니다. 쌓는 순서는 채점하지 않습니다.
채점은 하나의 불투명한 숫자가 아니라 **항목별 결함 목록**으로 나옵니다.

| 결함 | 감점 | 결과 |
|---|---|---|
| 빠진 재료 | 빠진 비율만큼 | |
| 안 시킨 재료 | 개당 20% | |
| 살짝 덜 익음 / 좀 탐 | 개당 18% | 값이 깎임 |
| **생고기** | 개당 55% | **반품 + 하트 −1** |
| **탄 패티** | 개당 55% | **반품 + 하트 −1** |

생고기나 탄 패티는 그 하나만으로 반품선(품질 48%) 아래로 떨어집니다 —
토핑을 아무리 잘 올려도 손님은 안 받습니다. 패티 두 장이 다 타면 더 깎입니다.

서빙 결과 배너에 **가장 심한 결함의 이름이 그대로 뜹니다** —
`SENT IT BACK! / THAT PATTY IS BURNT`. 이유 없이 반품당하면 게임이 불공정하게 느껴지니까요.

`cookFault()`는 점수가 아니라 **패티가 실제로 보이는 상태**(`cook` + `char`)로 판정합니다.
화면에서 새까맣게 보이면 새까만 걸로 채점됩니다.

### 그릴

패티는 접시에 바로 못 올립니다. 그릴에 올리고, 초록 구간에서 다시 가지러 가야 합니다.

```
[  raw  ][ P E R F E C T ][ over ][ burnt ]
             ↑ 여기서 집기
```

기본 초록 구간이 1.6초, `Pro Grill`로 3.25초까지 넓어집니다.
타이밍을 놓쳐도 최소 30%는 받습니다 — 완전히 날리진 않습니다.

**패티는 실제로 익어가는 게 보입니다.** 재료통 속 고기도, 그릴로 나르는 동안 손에 든 고기도
지방이 낀 **생고기(분홍빛)** 입니다. 그릴 위에서 서서히 갈색이 되고, 초록 구간에서 격자 자국이
생기고, 방치하면 숯이 됩니다. 덜 익은 채로 접시에 올리면 접시 위에서도 덜 익어 보입니다.

굽기는 **점수와 외형을 분리**해서 다룹니다. 점수용 `cookQuality`는 구간을 지나면 다시
내려가는데(타면 점수가 깎이니까), 그 값으로 색을 칠하면 **탄 패티가 다시 생고기 색으로
돌아갑니다.** 그래서 외형용 `cookLook`은 익음(`done`)이 절대 되돌아가지 않고,
탄 정도(`char`)를 따로 올립니다.

## 디자인 시스템 — Organic

껍데기는 Claude Design의 **Organic** 시스템으로 다시 입혔습니다
(`claude.ai/design`). 크림–샌드 바탕, 테라코타 강조색, **세이지를 진짜 두 번째
목소리로** 쓰는 팔레트에 Caprasimo 디스플레이 + Figtree 본문, 16px에서 시작해
알약(999px)까지 가는 라운드.

색·간격·라운드·그림자는 전부 `css/style.css` 맨 위의 토큰에서 나옵니다.
램프에 이미 있는 값을 하드코딩한 곳은 없습니다.

- **어두운 껍데기를 버렸습니다.** 원래는 어두운 앱 안에 밝은 주방만 창처럼
  뚫려 있었는데, 그러면 앱은 밤의 오락실이고 주방만 낮이었습니다. 크림으로
  통일하니 전체가 **햇빛 드는 모퉁이 버거집 하나**가 됩니다.
- **알람 역할은 게임이 추가한 것입니다.** Organic은 강조색 두 개만 주고 위험색이
  없는데, 주방 게임은 "이건 잘못되고 있다"를 강조색과 헷갈리지 않게 말할 수
  있어야 합니다. 같은 따뜻한 색상군, 같은 밝기 단계로 `--color-alarm-*`를
  얹었습니다 — 탄 패티, 깎인 하트, 임대료 줄, 마지막 15초.
- **캔버스도 같은 두 서체를 씁니다.** 캔버스는 CSS 변수를 프레임마다
  `getComputedStyle` 없이 못 읽으므로, `game.js` 상단의 `C` / `fontBody` /
  `fontDisplay`가 실제로 칠하는 단계만 복사해 둡니다 — 같은 값, 한 곳에서 조율.
  Figtree는 700에서 끝나니 900을 달라고 해서 합성 볼드를 받는 곳도 없앴습니다.
- **아이콘은 Lucide**(굵기 2.75)를 data URI 마스크로. 이모지는 크림 위에서
  세 개가 서로 다른 무게의 삽화로 도착해서, 타이틀 타일에서만 걷어냈습니다.
  마스크를 못 쓰는 환경에서는 이모지가 그대로 폴백입니다.
- **왼쪽 정렬.** 시트 제목이 전부 가운데였을 때는 어느 화면이나 "대화상자"로
  읽혔는데, 왼쪽으로 붙이니 같은 소책자의 다른 페이지처럼 읽힙니다.
- **앱 아이콘/스플래시도 같은 팔레트에서 다시 생성됩니다** (`npm run icons`).
  크림 정사각형 위에 부드러운 **세이지 원판**, 그 위에 버거 — 따뜻한 마크를
  따뜻한 바탕에 놓으면 밀 데가 없어서, 시스템이 아껴둔 두 번째 목소리를
  여기 씁니다. 다크 스플래시는 같은 램프의 깊은 끝으로 따로 만듭니다.
- **서체만 유일한 외부 요청입니다.** 나머지는 여전히 에셋 0개고, 폰트는
  `display=swap` + 실제 폴백 스택이라 네트워크 없는 첫 실행도 레이아웃이 같습니다.
  스토어 빌드 전 `www/fonts/`로 내재화하는 방법은 [DEPLOY.md](DEPLOY.md)에.

### 러시아워와 서빙 플래시

두 가지는 캔버스가 말할 수 없습니다. 한 스테이션이 아니라 **앱 전체**에 대한
이야기이기 때문입니다.

- **러시아워** — 전광판이 넘치기 직전이면 방 자체가 긴장합니다. 보드가
  테라코타로 데워지고 간판이 깜빡입니다. **BGM 편성이 읽는 것과 똑같은 압력
  숫자**를 읽으므로, 들리는 것과 보이는 것이 두 개의 사실이 아니라 하나입니다.
  경계선 양쪽에 히스테리시스를 걸어놨습니다 — 안 그러면 딱 걸친 보드가 깜빡거립니다.
- **서빙 플래시** — 판정이 나면 껍데기 전체가 0.5초 물듭니다. 들어간 접시는
  세이지, 반품된 접시는 토마토. 배너가 이미 이름을 말해주지만, 그릴을 보고 있던
  플레이어는 아직 고개를 안 들었습니다 — 물드는 건 그래도 닿습니다.

둘 다 게임이 없어도 되는 DOM 위의 장식입니다. 노드가 없거나 스텁에 `classList`가
없으면 조용히 넘어가고 영업은 계속됩니다.

## 아트 디렉션 — 2.5D

주방 안쪽은 **위에서 조명이 떨어지는 밝은 방**입니다. 어두운 갈색 위에 어두운
갈색 음식을 올려놨더니 아무것도 안 보였거든요. 이제 껍데기까지 크림이라
방과 앱이 같은 색 계열인데, 주방의 타일 벽(#f2e2c6)이 껍데기(#f5ead8)와 거의
같은 밝기여서 그냥 두면 방 윗부분이 페이지에 녹아버립니다. 그래서 캔버스에
**4px 테라코타 링**을 둘렀습니다 — 헤어라인이 아니라, 밝기가 아니라 **색상**으로
가르는 테두리.

입체감은 **가짜 3D(슬랩)** 로 냅니다. 아이소메트릭 격자로 갈면 좌표계·히트테스트·테스트를
전부 다시 써야 하는데, 같은 좌표를 쓰면서 두께만 주는 걸로 대부분의 효과를 얻습니다.

```
   ┌─────────────┐  ← 윗면 (그라디언트 + 상단 림라이트)
   │             │
   └─────────────┘
    ╲___________╱   ← 옆면 (어두운 색, 아래로 d픽셀 오프셋)
      ~~~~~~~~~      ← 바닥 접지 그림자 (blur)
```

- **조리대**가 구획마다 한 줄씩 놓이고, 재료통이 그 위에 얹힌 블록으로 올라갑니다.
  구획 사이로 크림색 타일 벽이 보입니다
- **그릴**은 진한 숯색 유닛에 화구가 파여 들어간 형태 (`well()`) — 안쪽에 잉걸불 글로우,
  패티에서 **김이 피어오릅니다**
- **접시대**는 흰 슬랩 위에 실제 접시(타원 3겹)가 놓이고 그 위에 버거가 쌓입니다
- **서빙 창구**는 밝은 다이닝룸이 비치는 창처럼 파여 있고, 접시를 들면 켜집니다.
  창 안에는 아무도 서 있지 않고 안내문이 개구부 한가운데에 들어갑니다 —
  아래 「얼굴을 뺐습니다」 참고
- 바닥은 체크무늬 + 조리대가 드리우는 접지 그림자 + 앞쪽으로 갈수록 밝아지는 조명
- 요리사는 **치비 비율** — 머리가 몸의 절반, 토크가 머리보다 큼.
  볼터치, 웃는 입, 랜덤 눈깜빡임, 도착할 때 스쿼시–스트레치 점프
- **드는 것은 전부 실제 사물입니다.** 아이콘을 카드에 담아 머리 위에 띄우는 게 아니라,
  치즈 한 장이면 치즈 한 장을, 완성된 버거면 접시째 허리 높이에 들고 두 손이 그걸 감쌉니다.
  `Art.drawChef`가 `carry` 콜백을 몸통·머리 다음, 손 그리기 직전에 호출해 z순서를 잡습니다
- 그리기 순서가 곧 깊이입니다: 벽 → 조리대 → 그릴/접시대 → **요리사** → 서빙 창구(제일 앞)

44px짜리 캐릭터에 사실적 비율을 쓰면 그냥 얼룩으로 보입니다. 과장이 정답이었습니다.

### 재료는 상자에서 꺼냅니다

처음엔 납작한 타일 위에 재료 그림이 떠 있는 형태였는데, 그건 컨테이너가 아니라 버튼이었습니다.
지금은 **뚜껑 없는 나무 상자**가 조리대 위에 한 줄로 늘어서 있습니다.

- 상자 몸통 + 안쪽으로 파인 **내부**, 위쪽에 안쪽 그림자
- 재료가 상자 **안에** 쌓여 있습니다. 개수는 고정이 아니라 **상자 높이의 58%를 채울 만큼**
  자동 계산됩니다 — 3개 고정이면 소스 통(2px 두께)은 텅 비어 보이고 빵은 넘쳤습니다
- **앞판을 재료 위에 덮어 그립니다** — 이게 없으면 재료가 상자 위에 얹힌 것처럼 보입니다
- 이름표는 앞판에, 구워야 하는 재료에는 붉은 태그

### 꺼내는 순간

재료를 집으면 **상자가 움찔하고, 재료가 포물선을 그리며 요리사에게 날아갑니다** (0.26초).
날아가는 동안 요리사의 손은 비어 있다가, 착지하면서 그대로 손에 들립니다 —
같은 물건이 두 곳에 동시에 보이지 않도록.

날아가는 재료의 도착 크기를 손에 든 크기와 **정확히 같게** 맞춰서 착지할 때 크기가 튀지 않습니다.
게임 상태는 탭한 즉시 바뀌고 애니메이션은 순전히 겉모습이라, 연출이 조작을 지연시키지 않습니다.

### 한 줄 진열

재료를 BUNS / TOPPINGS / SAUCES 세 선반으로 나눴다가 **한 줄로 합쳤습니다.**
선반 라벨이 차지하던 세로 공간이 상자로 돌아가서, 상자가 46px에서 80px로 커지고
비로소 "상자"처럼 보입니다. 정렬 순서는 그대로 빵 → 토핑 → 소스입니다
(`dayMenu()`가 이미 그 순서로 돌려주므로 라벨 없이도 줄이 정돈됩니다).

## BGM

**음원 파일을 가져오지 않고 작곡해서 넣었습니다.** 이 프로젝트는 에셋 0개 구조이고,
받아온 음원은 플레이스토어 배포에 저작권 문제를 남깁니다. 생성된 루프는 그럴 일이 없습니다.

- 워킹 베이스(4분음표) + 킥 + 하이햇 + 오프비트 코드 스탭
- **주방이 바빠질수록 편성이 두꺼워집니다** — 스네어가 들어오고, 코드 스탭이 늘고,
  압박이 심해지면 멜로디 라인이 올라옵니다.
  강도는 `전광판이 찬 정도 × 0.45 + 가장 위험한 티켓의 초조함 × 0.55`
- `setTimeout`은 그루브를 유지하기엔 너무 불안정해서, WebAudio 클럭 기준
  **룩어헤드 스케줄러**(30ms 간격으로 140ms 앞을 예약)로 짰습니다
- 일시정지·탭 백그라운드에서 스케줄러를 정지합니다 —
  백그라운드 탭의 스로틀된 클럭에 계속 예약하면 복귀할 때 음이 한꺼번에 쏟아집니다
- 음소거 토글이 그대로 적용됩니다 (같은 마스터 게인을 탑니다)

테스트가 가짜 AudioContext를 물려 스케줄러를 손으로 돌리면서, 4초 동안 음이 실제로
예약되는지 / 과거 시각에 예약하지 않는지 / 루프가 64스텝을 벗어나지 않는지 확인합니다.

## 밸런스는 추측이 아니라 시뮬레이션으로

`core.js`에 DOM이 하나도 없어서 Node에서 하루를 수천 번 돌릴 수 있습니다.

| | 정확도 | 굽기 | 속도 | 이탈 | 임대료 대비 |
|---|---|---|---|---|---|
| PRO | 97% | 1.00 | 0.70 | 0% | **x2.15** |
| DECENT | 84% | 0.88 | 0.45 | 5% | **x1.50** |
| SLOPPY | 45% | 0.55 | 0.15 | 25% | **x0.80** |

임대료는 그날이 실제로 생성하는 주문에서 샘플링하므로, 빵을 재료로 추가하거나
가격을 바꿔도 자동으로 따라옵니다. `the difficulty ramp does not drift across a full run`
테스트가 25일 내내 평탄함을 강제합니다.

### 이전에 "너무 어렵다"를 어떻게 고쳤나

| | 이전 | 지금 |
|---|---|---|
| 채점 | 쌓는 순서까지 일치 (LCS) | 재료 집합만 일치 |
| 주문 지정 | 티켓을 접시에 미리 고정 | 창구에서 자동 매칭 |
| 하트 | 3 | 5 |
| 1일차 | 손님 6명 / 44초 / 재료 6종 | **손님 4명 / 61초 / 재료통 2개 / 주문 = 빵+패티** |
| 실패 조건 | 1일차부터 하트 소진 가능 | 1일차는 손님(4) < 하트(5) — **하트로는 못 짐** |

시뮬레이션이 실제 문제를 하나 더 잡아냈습니다. 처음엔 정확도를
`맞은 개수 / max(주문, 만든 것)`으로 계산했는데, 이러면 **주문이 짧은 초반에
실수 하나가 전량 반품**이 되고 긴 후반엔 살아남습니다 —
서투른 플레이 기준으로 1일차 x0.40, 20일차 x0.82로 초반이 후반보다 가혹했습니다.
지금은 "주문한 것을 얼마나 맞췄나"를 먼저 보고 잉여 재료에 별도 감점을 붙입니다.

## 스모크 테스트가 잡아낸 것들

스텁 DOM에서 게임을 실제로 부팅해 돌리는 테스트라, 눈으로는 안 보이는 것들이 걸립니다.

- **게임 루프가 영구 정지하던 버그** — `draw()`에서 예외가 나면 `requestAnimationFrame`
  재등록이 안 돼서 게임이 그대로 멈췄습니다. 이제 프레임을 **먼저** 예약합니다
- **탄 패티가 아예 안 그려지던 문제** — `mixHex`가 `rgb(...)`를 반환하면서 `#rrggbb`를
  파싱했습니다. 생고기→시어→숯을 2단 블렌드하는데 두 번째 입력이 NaN이 되어 조용히
  아무것도 칠하지 않았습니다. 굽기 단계를 한 줄로 렌더해보고 나서야 보였습니다
- **임대료가 11일차에 내려가던 문제** — 그날 로테이션 메뉴가 싸서. 래칫을 걸었습니다
- **작은 화면에서 스테이션이 찌그러짐** — 방 스케일 계수가 확대만 가능해서(1.0~1.5)
  선반이 3줄로 늘면 그릴·접시가 20px 아래로 눌렸습니다. 0.72~1.5로 확장
- **재료통 아이콘이 캔버스 원점에 한 번 더** 그려지던 중복 호출
- **`drawIcon`의 `clearRect`** 가 요리사가 든 물건 뒤 배경에 구멍을 뚫던 문제

## 상점 아이콘과 버거 쌓기 — 디자인 핸드오프에서

「Mr. Burger 디자인 요청」 프로젝트의 `주방과 UI 디자인.dc.html` / `game-art/art.js`에서
아직 안 들어와 있던 두 덩어리를 가져왔습니다. (주방 아트·바닥 6종·아이템칸은 이미
적용돼 있었고, 손님 14종은 일부러 두고 왔습니다 — 위 「얼굴을 뺐습니다」 참고.)

**상점 아이콘 5종.** 상점만 이모지(👟🍽️🔥🍳💡)를 쓰고 있어서, 그 화면에서만 게임이
그린 손이 사라지고 기기 폰트가 튀어나왔습니다. `Art.drawUpgrade`가 같은 펜으로
그립니다. 뜻이 겹치던 **Pro Grill**과 **Extra Burner**는 **불꽃**과 **화구 한 판**으로
갈라서, 아이콘만 보고도 "더 잘 굽는다"와 "하나 더 굽는다"가 구분됩니다.
날짜별 상점과 유료 상점(THE OUTFITTERS)의 기어 배지가 같은 그림을 씁니다.

**버거가 붕 뜨던 문제.** 레이어를 칸(box)에 맞춰 쌓다 보니 그림과 칸 사이 여백이
그대로 틈이 됐습니다. 아보카도 부채는 제 칸 바닥에 닿지도 않았고요. 이제 레이어마다
**실제로 잉크가 칠해지는 범위**를 잰 표 두 개를 씁니다.

| 표 | 무엇 |
|---|---|
| `SEAT` | 그 레이어가 **단단한** 구간 — 다음 레이어가 내려앉는 면 |
| `PAINT` | 마지막 픽셀까지의 **칠해진** 구간 |

둘은 다른 질문입니다. 하나로 겸하면 스택 높이가 몇 % 모자라게 잡히고, `fitWidth()`로
칸에 맞춘 버거는 **윗빵 정수리가 잘립니다.** `biteBetween()`이 파고드는 깊이를
양쪽 두께에서 뽑되 얇은 쪽 기준으로 상한을 둬서, 6px짜리 소스 줄 위에 얹힌 윗빵이
공중에 뜨지도 않고 소스를 덮어버리지도 않습니다.

## 못 쓰는 업그레이드를 팔고 있었습니다

주방은 날짜만으로도 알아서 커지고(17일차에 접시 +1, 19일차에 화구 +1),
방 전체는 스테이션 5개에서 막힙니다. 그래서 **19일차부터 두 번째 `Extra Burner`는
설치될 자리가 없습니다** — `2 + 2(날짜) + 2(구매) = 6 → 5`로 잘립니다.
그런데 상점은 버튼을 켜둔 채 **돈을 받고 있었습니다.** 화구는 끝내 안 나옵니다.
두 번째 `Plating Station`도 17일차부터 같습니다.

`upgradeGains(id, day, levels)`가 "이 다음 레벨이 그날 뭐라도 바꾸나"를 묻습니다.
한 필드가 아니라 **`effects()` 전체를 비교**해서, 나중에 다른 업그레이드에 상한이
생겨도 조용히 재발하지 않습니다. 상점은 `내일` 기준으로 묻고(구매가 반영되는 게
다음 날이니까), 안 바뀌면 `FULL`로 잠그고 「The kitchen is already full」을 붙입니다.
`buyUpgrade()`에서도 한 번 더 막습니다 — 마크업만 고치는 건 UI지 규칙이 아니라서요.

테스트가 1~25일차 × 전 업그레이드 × 전 레벨을 돌면서 `upgradeGains()`와
`effects()`의 실제 변화가 일치하는지 확인하고, 상한이 무는 두 지점(19일차 화구,
17일차 접시)을 이름으로 못박습니다.

## 얼굴을 뺐습니다

손님 얼굴은 두 곳에 있었습니다 — 티켓 맨 위의 흉상, 그리고 서빙 창구 안에 서서
인내심이 줄면 표정이 굳던 사람. **둘 다 걷어냈습니다.**

- **티켓** — 이제 버거 그림 + 재료 이름 + 인내심 바뿐입니다. 티켓이 답해야 할
  질문은 “뭐가 들어가나”이고 얼굴은 거기에 대답하지 않습니다.
- **창구** — 안내문이 **개구부 한가운데**로 올라왔습니다. 원래는 얼굴을 피하려고
  창틀 아래에 밀려나 있었고, 그래서 작고 어두운 나무 위에 얹혀 있었습니다.
  이제 어둑한 방을 배경으로 밝은 글씨입니다.

전광판이 그만큼 줄었습니다. 얼굴 24px + 간격 3px이 예약 높이에서 빠지면서
**전광판 176 → 153px**, 그 자리가 그대로 주방으로 갑니다 (375×667에서 **주방 330 → 347px**).

**손님 캐릭터 아트도 통째로 걷어냈습니다** — `art.js`에서 327줄
(`drawGuest` / `drawGuestProp` / `drawGuestFace` + 열네 명의 팔레트 표),
`game.js`에서 배역 캐스팅(`GUEST_CAST` / `castGuest`), 그리고 코옵 스냅샷의
`g` 필드까지. 아무도 안 부르는 코드를 "되돌릴지도 모르니까"로 남겨두면 그건
그냥 죽은 코드입니다. 되살리려면 git에 있습니다.

손님 **성격**은 그대로입니다 — `Core.CUSTOMERS`의 다섯 원형이 여전히 인내심과
팁을 정하고, 이탈 배너에 이름이 뜹니다(`Rush gave up waiting`). 사라진 건 얼굴이지
사람이 아닙니다.

성급한 손님(`rush`)의 떨림은 얼굴에 걸려 있었습니다. 이제 티켓에서 흔들릴 수 있는
건 버거뿐이라 거기로 옮겼습니다.

## 상점 — 파는 것, 그리고 일부러 안 파는 것

`THE OUTFITTERS`. 상품 모양은 **셋뿐이고 넷째는 없습니다.**

| 종류 | 무엇 | 밸런스 |
|---|---|---|
| **스킨** | 요리사의 색 11개를 갈아끼움 | 시뮬레이션이 재는 것에 영향 0 |
| **기어** | **이미 있는** 업그레이드 트랙의 레벨 1개 | 그 트랙의 기존 `max`에서 멈춤 |
| **금고** | 게임 내 현금 | 상점 총액도 스테이션 상한(5개)도 그대로 |

이 파일의 25일 곡선은 추측이 아니라 시뮬레이션으로 맞춘 것이고, **틀어지면 실패하는
테스트가 있습니다.** 그래서 돈으로 파는 것 중 새 능력을 만들거나 천장을 올리는 건
하나도 없습니다. `Non-slip Clogs`를 사는 건 어차피 벌었을 Running Shoes 레벨을
**먼저** 갖는 것이지 **더** 갖는 게 아닙니다 — `levelsWithGear()`가 산 레벨과 번
레벨을 같은 바구니에 넣고, 그 바구니는 커지지 않습니다.

테스트가 이걸 강제합니다.

- `paid gear reaches a track sooner, never further` — 만렙 트랙에 기어를 얹어도
  만렙이고, **`effects()`는 산 레벨과 번 레벨을 구분하지 못합니다.** 따로 곱해지는
  유료 배수가 없으니 드리프트할 것도 없습니다.
- `the store only sells cosmetics, existing upgrade levels, and cash` — 넷째 종류가
  생기면 실패합니다. 카탈로그 한 줄이 아니라 밸런스 결정이니까요.
- `a save cannot invent a purchase or wear what it does not own`

**가격은 코드 어디에도 없습니다.** 지역·세금·프로모션은 스토어가 관리하니
`"$2.99"`를 박으면 첫날부터 어딘가에서 틀립니다. 카드는 스토어가 준 문자열을
그대로 쓰고, 아직 안 왔으면 **티어 동전 3개**가 상대 가격을 대신 말합니다.

**결제는 아직 연결돼 있지 않습니다.** `www/js/billing.js`가 이음매고 지금은
샌드박스 어댑터가 돕니다 — 아무것도 청구하지 않고, 상점 화면이 그 사실을 자기
입으로 말합니다. 붙이는 절차와 Play 정책은 [DEPLOY.md](DEPLOY.md)에.

그리고 **새 가게를 시작해도 산 것은 안 지워집니다.** 진행도는 리셋이지만 영수증은
아니니까요 (`wipe()`가 소유를 바로 다시 씁니다).

## 놓는 순간도 애니메이션입니다

집는 쪽은 원래 있었습니다 — 상자가 움찔하고 재료가 요리사에게 날아옵니다. 놓는 쪽은
없어서, 패티가 주먹에서 그릴로 **두 프레임 사이에 순간이동**했습니다. 그게 주방을
장소가 아니라 상태 기계처럼 느껴지게 하던 것이었습니다.

이제 `dropOnto()`가 반대 방향으로 같은 포물선을 그립니다 (0.2초). 규칙은 도착 즉시
이미 적용됐으므로 — 손은 비었고 접시엔 재료가 올라가 있고 — 이건 순전히 **물건이
여정을 끝내는 것**입니다. 손에 들려 있던 크기에서 놓일 크기로 줄어들면서 내려앉습니다.

두 가지가 이걸 성립시킵니다.

- **`fixed`** — 들어오는 비행체는 아직 걸어오는 중인 요리사를 쫓아가야 하고,
  나가는 비행체는 절대 그러면 안 됩니다. 목적지는 움직이지 않으니까요.
- **`inbound()`** — 아직 오고 있는 물건은 목적지가 **그리지 않습니다.** 이게 없으면
  같은 치즈 한 장이 0.2초 동안 손과 접시 양쪽에 동시에 보입니다 —
  애니메이션이 아예 없는 것보다 나쁩니다. 집는 쪽이 "착지할 때까지 손을 비워두는"
  방식으로 푸는 것과 같은 문제입니다.
